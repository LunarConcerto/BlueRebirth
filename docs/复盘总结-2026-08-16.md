# 苍蓝誓约 JP 1.4.0 逆向复盘总结

> 2026-08-16 会话复盘。目标是沉淀整个流程里**有用、可复用**的逆向成果，作为重做流程的知识底座，并记录死胡同的原因，避免重蹈覆辙。

## 1. 目标与整体架构

**目标**：让日服客户端 `blueoath.exe`（1.4.0）离线运行，连本地服务器（`127.0.0.1`，KCP/UDP 7201），跑通「SDK 登录 → 服务器列表 → 选服 → 游戏 socket 登录」闭环。

**基础设施**：
| 组件 | 作用 |
| --- | --- |
| `BlueOath.Server` | 本地 TLS/HTTP/KCP 服务器（登录 + 服务器列表 + KCP 游戏登录，端口 7201） |
| `BlueOath.Injector` + `BlueOath.Payload` | x86 注入 DLL（xinput 劫持）：SDK 边界 hook、网络重定向（DNS/connect/TLS）、TLS 信任补丁 |
| `BlueOath.Tools` | IL2CPP 元数据解析、methodPointers 定位、RVA 目录 |
| `lua_tools/BlueoathLua` | 国服 1.5.20 反编译 Lua 源码（交叉验证用） |

## 4. IL2CPP 调用约定（关键）

- **实例方法**：`this` 在栈上第一个参数 `[esp+4]`（即 `[ebp+8]`），**不是 ECX**。
- **静态方法**：`(MethodInfo*, args...)`，`MethodInfo*` 是第一个参数。
- **虚调用**：vtable 有 **4 字节头**（type 指针），方法槽从 `0x4` 开始，每槽 8 字节（`methodPtr@0x4+slot*8`、`method@0x8+slot*8`）。StageBase 的 Slot 17（StageTick）因继承 MonoBehaviour/Object 占了前置槽，运行时 vtable 偏移更大。
- **IL2CPP 字符串**：对象布局 `klass@0x0 / monitor@0x4 / length@0x8 / chars@0xC`（UTF-16）。字符串字面量引用可能走 relocation，**直接搜字符串地址在 .text 里搜不到**。

## 10. 当前阻塞点（根因，已定位到精确指令）

**根因**：UI 场景（UIPageManager 等 MonoBehaviour 单例）从未加载 → 场景单例全 NULL → `StageBase.Tick` 的 Loading 分支解引用 NULL → 主线程冻结。

**精确冻结点**（本轮修正 status.md 的旧结论）：
```
StageBase.Tick(0x1EA600) Loading 分支：
  0x1EA6A6: mov eax, [0x11d2c498]      ; 场景单例 = NULL
  0x1EA6AB: test byte [eax+0xc2], 1    ; ★ 空指针解引用 → 冻结（不是 0x1EC05B）
```

- 另有同源点 `0x1EA736`（edi==0 路径）和 `0x101FB180` 内部（读 `[0x11d2c498]`）。
- 之前 null-guard Patch 1 打在 `0x1EC05B`（StageTick state 0），**打错位置**（永远执行不到）。
- 运行时 poll 证实：`[0x11d269a4]=NULL [0x11d269c8]=NULL [0x11d2c42c]=NULL [0x11d2c498]=NULL`、`NetLogic.instance=NULL`。

## 12. 两条技术路线（已备份删除的 hook 逻辑）

| 维度 | redirect（`bypass=0`） | bypass（`bypass=1`） |
| --- | --- | --- |
| SDK | 真实跑（originalInitSdk/TickLoop/Login/GetHash） | 完全假（TickLoop 不调原函数，手动派假事件） |
| SDK 回调 | 依赖真实异步链（本地不稳定） | 手动派发 init=1/switch=27/applereview=19/platformdata=1007/login=2 |
| 登录链 | 游戏自然流程（Lua 状态机） | payload 直调 C#（Login→GetServiceList→GetLastServiceList→SelectService→Connect） |
| simulation mode | 用（跳过 login，hash 走 /gethash.php） | 不用 |
| 共同点 | 都开网络重定向 + TLS 信任补丁 | 同左 |
| 卡点 | login 从未被调（SDK 回调不派发） | Connect 空指针 / 场景卡死 |

- `[redirect] enabled=1` 是基础设施（DNS/connect/TLS 重定向 + 证书信任），两模式都开；`[sdk] bypass=1` 是额外 SDK 绕过开关。
- redirect 模式唯一的 hybrid 手动注入：`getPlData` → event 1007（因为 SDK 自己异步不派发）。

## 13. 方法论教训（重做务必遵守）

1. **运行时 hook 读内存 > 静态反查 IL2CPP 元数据结构**（fieldOffsets 运行时才初始化、metadataUsage 编码对不上、images 表结构不明——静态查性价比极低）。
2. **每加一个 hook 可能扰动时序**，导致冻结点漂移（frame 1 ↔ frame 3）。诊断和功能 patch 必须拆开、可开关。
3. **hook stolen-length 铁律**：5 字节跳转（E9+rel32）覆盖 `addr..addr+4`，所以 stolenLen 必须 ≥5 且落在完整指令边界，否则回跳目标落在跳转指令中间 → 垃圾代码 → 崩溃。
4. **回跳别破坏寄存器**：`mov eax,backTarget; jmp eax` 会破坏 EAX（导致 lateUpdate 崩溃），回跳用 `jmp rel32`。
5. **反汇编工具**：`pefile.get_memory_mapped_image()` 是 **RVA 索引**，不是文件偏移；别再 `RVA-0xC00` 去索引。
6. **IL2CPP 字符串引用可能走 relocation**，直接搜字符串地址在 .text 里搜不到——定位字符串消费者要用运行时 hook 或 relocation 解析。
7. **崩溃 dump 分析**是定位 hook bug 的金标准（`CrashDumps\blueoath.exe.*.dmp`，用 WinDbg/`!analyze -v` 看崩溃地址对到 RVA）。
8. **「满足自然流程」是无底洞**（场景加载是黑盒）；**硬 bypass 是有终点的方向**，但前提是拿到正确的对象图。

## 14. 死胡同复盘（为什么打转这么久）

1. **根因没咬死**：一直以为卡在「SDK 登录没触发」或「StageTick state 0」，实际是「UI 场景没加载 → StageBase.Tick Loading 分支解引用 NULL 冻结」。诊断 hook 越加越多，冻结点反而漂移。
2. **两条路线（bypass/redirect）都撞同一个根因**：UI 场景不加载。区别只是 SDK 层怎么假，场景层一样卡死。
3. **红鲱鱼**：`Enumerable.Last<object>` 调 `get_resLoadMgr`、`errornu=-1`、`User.sdkfinish`、`Dictionary.getItem`(0x1435D30) 都被当成线索追过，全是干扰项。
4. **没有先回答「谁触发 UI 场景加载」**这个根本问题，就去补 null guard / 硬 bypass，属于治标。

## 15. 候选重做方向

1. **定位「谁触发 UI 场景加载」**（根因）：运行时 hook `SceneManager.LoadScene` / `AssetBundle.LoadFromFile` / `Resources.Load`，或追 `ResLoadMgr.AddRes` 的接口调用者（IL2CPP 接口调度在 vtable，需 hook 而非静态 call 搜索）。目标是回答：正常流程里 UI 场景（含 UIPageManager）由谁、在哪一步 AddRes。
2. **硬 bypass 直连**（终点）：直调 `NetLogic.Connect`（自建对象图，已确认可行方向），跳过场景，先打通游戏 socket 登录，验证 M3/M4 的 KCP wire format。
3. **原生启动 + 内存 dump**：按正常流程启动（不注入），从内存 dump Unity `SceneManager` 已加载场景列表 / `ResLoadMgr` 队列，反推 UI 场景加载触发点。
4. **最小化重做原则**：新 payload 只保留「网络重定向 + TLS 信任 + 单一明确的诊断目标」，一次只验证一件事，杜绝十几个探针 hook 叠加。

## 16. 纯重定向重做（方向 1 落地，2026-08-16 后半场）

选了「纯重定向」路线：payload 只做网络重定向 + TLS 信任，不碰 GameAssembly 的 C# 逻辑，游戏按原有逻辑自然跑；本地服务器正确处理所有请求返回正确值。

### 16.1 最小 payload 重写

`hooks.cpp` 从 167KB 缩到 ~15KB，只保留：
- `getaddrinfo` DNS 重定向（`.blueoath.com`/`.zuiyouxi.com`/公网IP探测 → 127.0.0.1）
- 证书信任（进程内 ROOT store）+ `UnityPlayer.dll` `0x8E1573` TLS 补丁
- SDK 的 libcurl 补丁（TLS 校验关闭 + HTTPS→HTTP 降级，`sdk_ui_win32xx.dll`/`new_sdk.dll`）
- UDP 日志（sendto/WSASendTo/recvfrom）

### 16.3 getPlData 崩溃根因（关键突破）

SDK 处理 getPlData 响应时抛 C++ 异常（异常码 `0xE06D7363`），生成崩溃 dump（`%LOCALAPPDATA%\bt_dump\*.dmp`）。用 minidump 解析 + 栈回溯 + 反汇编定位：

```
异常类型: "Type is not convertible to int" (new_sdk.dll+0x52460)
抛点: new_sdk.dll+0x3347d (JsonValue::asInt 的 throw 分支)
调用链: tickLoop(0x3ab17) → 0xdcaf → 0xfdf5 → 0x1b446 → 0x2719c → asInt(0x333e0)
异常对象: new_sdk.dll+0x5a86c (静态)
```

**根因**：SDK 的 JSON 库 `asInt()` 把响应的 `errornu` 当 int 转，但服务器返回的是字符串 `"0"` → 抛异常。

**修复**：服务器所有端点 `"errornu":"0"` → `"errornu":0`（数字）。修复后 SDK 不再崩溃。

### 16.7 方法论补充

- **崩溃 dump 分析是定位 SDK 内部 bug 的金标准**：minidump 的 ExceptionStream 拿异常码/地址，MemoryListStream 读内存，ModuleListStream 定模块（注意模块名是 UTF-16 MINIDUMP_STRING），ThreadInfoList/ExceptionStream 的 ThreadContext（MINIDUMP_LOCATION_DESCRIPTOR = DataSize+Rva）拿 EBP/EIP/ESP，沿 EBP 链栈回溯即可定位抛点。
- **SDK 的 JSON 库有类型强校验**：`asInt()` 对字符串字段抛异常。服务器响应字段类型必须与 SDK 解析类型一致（errornu 是数字，不是字符串）。
- **PowerShell 改 UTF-8 文件要用 `-Encoding UTF8` 且源文件本身是 UTF-8**，否则中文注释会 mojibake；改 .cs 源码里的转义引号要用精确字符串替换（`\"errornu\":\"0\"`），别用 PowerShell 的 `-replace` 去碰非匹配文本。
